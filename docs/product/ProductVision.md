# Product Vision

本文件是 Kuro 的長期產品方向基線。它描述 Kuro 最後要成為什麼、主要服務誰，以及哪些方向即使短期看似方便也不應採用。

## 最終產品一句話

Kuro 是一個為單一使用者高度客製、local-first 的個人 AI 工作經理：它持續整合學習、市場、新聞與其他專案的狀態，判斷今天該注意什麼、該做什麼，再透過工作面板、角色互動與分層播報協助使用者採取下一步行動。

## 產品定位

Kuro 不是通用型公開產品，也不是只有聊天、陪伴或角色表演的桌寵。

Kuro 的核心任務是成為使用者的資訊整理中樞與工作經理：

- 收攏分散在不同專案、工具與資料來源的狀態。
- 區分重要、緊急、待追蹤、可延後與僅供參考的資訊。
- 把資訊轉成今天可理解、可排序、可採取行動的工作項目。
- 在值得注意的事情發生時主動提醒，但不強迫使用者接收完整內容。
- 讓使用者可以從簡短概要進入詳細資料、Reader、Briefing 或對應外部專案。
- 保留自然對話與角色互動，使工作助理可以長期常駐，而不是只在特定頁面被動使用。

Kuro 可以高度貼合單一使用者的習慣、專案與本機環境。這種個人化不代表可以犧牲可維護性、資料邊界、可回復性與工具安全。

## 核心使用者

Kuro 的主要使用者是本機擁有者本人。

產品設計預設：

- 單一使用者，而非多人、團隊或多租戶服務。
- 主要運行在使用者自己的 Windows 電腦與 local runtime。
- 可以理解並延續使用者的專案、學習目標、關注市場、資訊偏好與工作節奏。
- 優先服務實際日常使用，不為了對外展示、通用化或陌生使用者 onboarding 犧牲個人工作效率。
- 長期記憶必須可審計、可修改、可停用與可刪除；高度個人化不能等同不受控地保存所有資訊。

## Kuro 要解決的核心問題

使用者的資訊與工作分散在學習系統、市場工具、新聞來源及其他專案中。即使每個專案都能整理自己的資料，使用者仍要逐一打開、理解並決定先做什麼。

Kuro 要補上的不是另一份摘要，而是跨來源的優先順序與行動脈絡：

- 今天最重要的事情是什麼。
- 哪些進度落後、資料有異常或情況突然改變。
- 哪些事情現在需要處理，哪些可以稍後再看。
- 為什麼 Kuro 認為這件事值得注意。
- 使用者接下來可以查看、執行或忽略什麼。

## 核心工作流

### 1. 每日工作管理

Kuro 整合當日狀態，主動整理：

- 今天最重要的事項。
- 尚未完成或進度落後的工作。
- 新出現的風險、異常或待確認事項。
- 建議的處理順序與下一個最小行動。

Kuro 的輸出不能只是資料列表；它必須讓使用者快速知道「現在先做什麼」。

### 2. 學習進度

Kuro 讀取學習專案提供的狀態，協助使用者理解：

- 目前進度與既定目標的差距。
- 今天應完成的學習內容。
- 哪些項目需要複習、補課或持續追蹤。
- 一段時間沒有進展時，是否需要重新安排。

學習內容與進度真相由對應學習專案負責，Kuro 負責跨日整理、提醒與安排優先順序。

### 3. 市場追蹤

Kuro 消費 OMI 提供的市場狀態、證據、限制與決策結果，協助使用者掌握：

- 今天值得注意的市場與自選標的。
- 突發重大消息、狀態改變或風險。
- 哪些資料仍是 stale、partial、missing 或有 provider failure。
- 是否值得進一步打開詳細研究或請 OMI 產生分析。

Kuro 不自行重做市場分析、freshness、provider fallback 或交易判斷。

### 4. 新聞追蹤

新聞能力完成後，Kuro 應先提供可掃描的標題與重要性概要，再讓使用者決定是否展開全文、摘要、來源或相關影響。

Kuro 應協助去除重複與低價值噪音，但不能因為濃縮內容而隱藏來源、時間、不確定性或相反證據。

### 5. 跨專案協作與自然互動

其他專案可以透過明確的 API、MCP 或本機 adapter 對外提供能力，讓 Kuro 查詢、整理與呈現。

Kuro 同時保留一般對話能力。使用者不需要先理解底層專案或工具名稱，可以直接說明需求，由 Kuro 判斷應查看哪個專案、呈現在哪個介面，以及是否需要進一步確認。

## 第一屏必須成立的體驗

Kuro 的產品主體是工作面板，不是工程用 Launcher，也不是只展示 Live2D 角色的空白畫面。

使用者打開 Kuro 後，第一屏應能立即回答：

- 今天最重要的三到五件事是什麼。
- 學習、市場與新聞目前各有什麼需要注意。
- 哪些項目需要使用者決定、查看或採取行動。
- 哪些來源尚未更新、資料不完整或暫時不可用。

工作面板應保持安靜、清楚、可掃描。角色作為助手／經理存在於體驗中，可以說明與提醒，但不能遮擋或取代主要工作資訊。

Launcher 應逐步回到 runtime 管理與診斷角色，不作為長期產品的主要工作入口。

## 主動提醒模式

Kuro 可以主動提醒，但必須採漸進式揭露，不直接把完整報告、長篇新聞或市場內容全部說完。

標準互動節奏：

1. Kuro 偵測到值得注意的狀況。
2. 先提供一段短概要，說明發生什麼、為什麼值得注意，以及資訊類型。
3. 詢問使用者是否要查看或聽取詳細內容。
4. 使用者同意後，再透過對話、Reader、Briefing 或對應專案展開。
5. 若存在可採取的行動，先提出選項；涉及寫入、發送、刪除、發布或大量 quota 時，依使用者為該能力設定的授權等級執行。未明確開放受限自動化時，預設仍需確認。

提醒品質優先於提醒數量。相同事件應去重，低重要度資訊不應頻繁打斷使用者；不確定或資料不足時要直接說明。

## 角色與工作延續

不同角色代表不同的人物、聲音、人格、語氣、表情與互動感受，但它們執行相同的工作。

切換角色後：

- 當日工作、Briefing、待辦、工具狀態與專案脈絡可以承接。
- 工具能力、權限、確認政策與資料邊界保持一致。
- 不應因角色不同而形成彼此隔離、互相矛盾的工作世界。
- 角色可以保有自己的表達偏好與互動記憶，但不得改寫共享的使用者工作事實。

產品應呈現為「同一個工作系統由不同人物接班」，而不是每換一個角色就重新開始。

## 外部專案關係

Kuro 是跨專案的工作入口與資訊整理者，不是所有 domain logic 的集中式後端。

- OMI 負責市場資料、freshness、證據與市場分析。
- 學習專案負責課程、進度與學習資料真相。
- 新聞系統負責來源取得、時間、去重與內容證據。
- 未來的 mail、calendar、tasks 或其他專案各自負責自己的資料與寫入規則。
- Kuro 負責把這些結果轉成統一的優先順序、提醒、Briefing、Reader 與自然語言互動。

新增外部能力時，應透過清楚的 contract 接入，不把該專案的商業邏輯複製進 Kuro prompt、Launcher 或 Electron UI。

## 長期不做的事

- 不以通用型公開 SaaS、多租戶或陌生使用者需求作為主要產品方向。
- 不把 Kuro 做成只有聊天、陪伴、角色展示或 Live2D 技術 demo。
- 不取代 OMI、學習、新聞或其他專案的 domain backend。
- 不讓 Kuro 自主交易；交易能力即使未來存在，也必須是獨立、明確的使用者操作與安全邊界。
- 不讓 Kuro 在缺少明確授權範圍、條件、額度與 audit 的情況下發送訊息、發布內容、刪改資料或執行其他高風險外部動作。使用者可以對特定能力開啟受限自動化，但不能等同全域放行。
- 不把所有工具結果、每日狀態與新聞自動寫入長期記憶。
- 不用無上限通知、長篇口播或頻繁彈窗製造「很主動」的假象。
- 不因切換角色而遺失工作狀態、建立互不相容的工具權限或重複保存同一份使用者事實。
- 不為了高度個人化而硬編碼 secrets、私人機器資料或不可回復的 local state。

## 必須反駁的方向

遇到下列方向時，應先指出衝突並提出安全替代方案：

- 為了角色效果或視覺展示，犧牲工作面板、資訊可讀性或任務處理效率。
- 把市場、學習、新聞、郵件或行程邏輯塞進角色 prompt 或展示層。
- 讓 Kuro 只彙整資料，不判斷重要性、優先順序或下一步。
- 為了主動感直接播放完整內容，不先提供概要與選擇權。
- 讓不同角色擁有彼此衝突的工作事實、工具政策或安全權限。
- 為了方便而繞過確認流程、tool policy、記憶審核或 audit trail。
- 用 frontend wording 掩蓋 stale、partial、missing、offline 或 provider failure。
- 在 ownership 與資料 contract 尚未固定前進行 Big Bang rewrite。

## 成功樣貌

Kuro 達到產品目標時：

- 使用者打開工作面板後，不必逐一檢查其他專案，就能知道今天最該處理的事情。
- 學習、市場、新聞與其他來源可以被放進同一個優先順序，但仍保留各自的證據與限制。
- 發生重大狀況時，Kuro 能主動給出短概要，並讓使用者決定是否展開。
- Kuro 不只回答「有什麼資料」，還能說明「為什麼重要、現在建議先做什麼」。
- 切換角色後，工作、進度、Briefing 與待辦可以自然承接。
- 新專案可以透過穩定 contract 接入，而不必重寫 Kuro 核心。
- Kuro 可以長期在本機穩定運行，遇到資料或 runtime 問題時能誠實顯示狀態並提供可理解的恢復線索。
- 高度個人化、角色體驗、工作能力、安全邊界與可維護性可以同時成立。
